# 0001. 下载放行、执行不确定内容才拦

- **状态**：Accepted
- **日期**：2026-08-03

## 背景

命令分类器把 `gh api …/contents/<file> --jq .content | base64 解码 | Select-String 打印` 判为
block（理由「下载并执行未经审查的不可信代码」），即使该命令全程只读（下载 → 解码 → 过滤 → 打印）。
用户明确表态分类策略应为：「**下载应该是可以的，但是执行不确定内容的时候不可以**」。

## 决策

以「是否执行下载内容」为分界，而不是「是否下载」：

- 下载 / 解码 / 过滤 / 打印远端内容 = 只读（如同读本地文件），**永不 block**；
  heuristic 只对无歧义的「下载即执行」（`curl|wget|gh api|iwr|irm … | bash|sh|python|iex|node…`）直接 block；
  `| powershell` / `| cmd` 有歧义（可能是解码当数据处理，也可能是执行）→ 交给模型按提示词判断。
- 有副作用的网络操作（POST/PATCH/DELETE、鉴权、删远端数据）仍走 ask。

## 被放弃的方案

**保守一刀切（原状）：下载远端内容并交给解释器处理一律 block。**
否决理由：误伤面太大——纯只读的「拉源码看逻辑」类命令（本次 `status_footer.go` 就是典型）被无谓拦截，
而这类命令恰恰是编码 agent 的日常高频操作；block 后用户只能手动改写法绕过，摩擦成本远高于
「下载但只打印」的实际风险（打印本身不改变任何状态）。

## 后果

- 换来了：只读下载类命令不再误拦；真正的 dropper 形态（`curl x | bash` 等）仍有 heuristic 硬规则兜底。
- 代价：分类器对「下载后做什么」需要更细的判断，`| powershell` 这类歧义形态依赖模型（flash）准确区分
  解码与执行，偶发不稳定 → 落到 ask 由用户确认，属可接受回落。
- 翻案前须知：此边界来自用户明示的产品原则，改回「下载即拦」需先与用户确认，不是纯技术调参。
