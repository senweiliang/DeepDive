# Codemap 字段规范（v2）

本文件是 codemap 知识库体系的**元规范**——定义每类文件的职责边界、产生触发器、写作规则、回写纪律。给维护 codemap 的人 / AI 看，不参与业务导航。AI 与协作人员新增或修改 codemap 文件时必须遵守。

> 一句话定位：codemap 是一套**纯 Markdown + agentic search** 的项目知识库。给一句 prompt（开发 X / 改 X / X 有 bug），AI 沿固定路由三跳拿到「最小充分上下文闭包」；靠回写纪律 + 定期审计与代码保持同步。不引入向量库——语料是策展过的、消费端是带 grep 的 agent、闭包优于 chunk 检索。

---

## 一、核心原则

1. **每类文件由它回答的问题定义**，不按重要性收内容。没有「什么都能塞」的桶。
2. **文件由压力产生，不由流程产生**：单元最小形态只有 nav.md；事实先塞 nav 卡，膨胀再抽 spec；红线被踩过才抽 attention。
3. **只写代码表达不了的事实**：why / 不变量 / 跨文件契约 / 历史事故。代码能表达的（签名 / 枚举值 / 字段）留指针「详见 `Xxx`」。**drift 面积正比于文档里复述代码事实的数量。**
4. **HEAD 原则**：spec 永远只反映当前形态，历史归 git / adr。
5. **递归导航**：进任何目录（模块 / 单元），第一步都是读该目录 `nav.md`。

---

## 二、分层与文件体系

```
docs/codemap/
├─ index.md                    全局路由（粗筛关键词 + 导航 SOP）
├─ SPEC.md                     本文件（元规范）
├─ codemap.config.json         工具配置（areas / srcDirs / 预算…）
├─ drills.md                   导航演练集（路由质检）
├─ tools/  check.py · staleness.py     自检脚本
├─ templates/                  起稿模板
└─ {module}/
   ├─ nav.md                   模块路由：读取规则 + feature/design 清单 + 关键词全集（模块层唯一必备）
   ├─ architecture.md          按需：跨单元分层图 + 全局不变量（能下放进 design 单元的必须下放）
   ├─ overview.md              仅当模块 nav 清单超一屏才建
   └─ feature/<x>/ · design/<x>/   单元（两者结构相同）
      ├─ nav.md                必有：门牌 + 上下文闭包
      ├─ spec.md               压力触发：契约 + 场景 + 不变量 + 落点 + 验证
      ├─ attention.md          事故触发：一行禁止句清单
      └─ adr/                  三原则触发：为什么选 A 弃 B
```

| 层级 | 文件 | 职责 | AI 读取策略 |
|------|------|------|------------|
| 路由层 | `index.md` | 业务模块路由 + 通用规范路由 + 导航 SOP | **每次代码任务的第一个工具调用** |
| 路由层 | `{module}/nav.md` | 模块内功能路由 + 关键词全集 | 定位模块后必读 |
| 摘要层 | `{module}/overview.md` | 20-30 行模块摘要 | 清单超一屏时建，需要时读 |
| 参考层 | `{module}/architecture.md` | 跨单元分层 / 数据流 / 全局不变量 | 需要全局细节时读 |
| 单元层 | `.../{feature,design}/<x>/nav.md` | 门牌 + 上下文闭包 | 定位到单元必读 |
| 单元层 | `.../<x>/spec.md` | 行为契约 + 场景 + 不变量 + 落点 + 验证 | 闭包点名时读 |
| 单元层 | `.../<x>/attention.md` | 一行禁止句清单 | 闭包点名时读 |
| 决策层 | `.../<x>/adr/` · `{module}/adr/` | 为什么选 A 不选 B | 闭包点名 / 推翻现状前读 |
| 模板层 | `docs/codemap/templates/` | 共享起稿模板 | 新建文件时复制 |

## 三、各文件字段规范

### 3.1 index.md — 全局路由

**职责**：业务模块路由 + 通用规范路由 + 导航 SOP。**AI 每次代码任务的第一个工具调用**。

| 字段 | 必填 | 说明 |
|------|:----:|------|
| 导航 SOP | 是 | 逐层读取步骤、推翻现状前查 adr、miss / 文档与代码不符时的回写触发 |
| 业务模块路由 | 是 | 每行：模块名、**代表性粗筛关键词**、nav.md 路径 |
| 通用规范路由 | 是 | 跨模块通用文档（语言规范 / 框架 / SDK / API） |

**index 行选词标准**：关键词的入选标准是**用户拿它当 prompt 第一个词的概率**，不是模块内的实现重要性。用户会说的词进 index；实现视角词（`instantiateFoo`）永不进 index。冲突词（多模块都有）多行并列，靠各自 nav 消歧。

**不含**：项目级事实、功能细节、类签名。

### 3.2 {module}/nav.md — 模块导航

**职责**：读取规则（SOP）+ feature/design 清单（任务 → 单元）+ 关键词全集（精筛）。关键词维护点集中在此。

| 字段 | 必填 | 说明 |
|------|:----:|------|
| 读取规则 | 是 | 本模块的逐层读取顺序 + 未命中回写触发 |
| feature 清单 | 是 | 每行：功能名、一句话、成熟度（⏳/✅） |
| design 清单 | 是 | 每行：机制名、一句话、成熟度 |
| 关键词全集 | 是 | 收**模型猜不到的词**（黑话 / 项目代号 / 精确标识符）；模型能语义联想的近义词不穷举——路由的检索器是模型本身 |

模板：[templates/module-nav.md](templates/module-nav.md)。预算 ≤80 行。

### 3.3 单元 nav.md（feature/<x>/ 或 design/<x>/）

**职责**：门牌（被找到）+ 上下文闭包（关联）。**不装事实**，事实在 spec。

| 字段 | 必填 | 说明 |
|------|:----:|------|
| 一句话 + 关键词 | 是 | 决定能不能被搜到 |
| 上下文闭包 | 是 | **每条 = 「触发条件 → 读什么」**——prompt 驱动分发的唯一机制 |
| 详情 | 是 | 指向 spec，标 ⏳/✅ |

模板：[templates/unit-nav.md](templates/unit-nav.md)。预算 ≤30 行；膨胀即抽 spec。

**上下文闭包关系词表**（闭包条目只用这几种关系，防各模块自造词）：

| 关系 | 含义 |
|---|---|
| 机制依赖 | 本单元调用的下层机制（→ design/） |
| 数据契约 | 遵守的数据形态（→ 拥有该契约的 design 单元） |
| 复用链路 | 复用了谁的实现 |
| 同源功能 | 与谁共享实现 / 语义 |
| 设计依据 | 为什么这么设计（→ adr / plan 存档） |
| 必读红线 | 碰某类操作前必读的禁止项（→ 拥有单元 attention / spec 不变量） |
| 范围边界 | 什么**不**属于本单元（防误改） |

**范围边界**只写「会走错门的」，不是枚举补集：仅当存在最近邻歧义（相邻单元共享关键词 / 数据 / 代码路径易走错门）**且事后发生过一次走错门**才写。每条 = 具体误解 + 正确去向。默认不写、整条省略。

### 3.4 spec.md

**职责**：单元的行为契约 + 用户场景 + 不变量 + 落点 + 验证。HEAD 当前形态。

**产生触发器**（任一即建，不等全满足）：
1. nav 卡事实超约 10 行；
2. 出过事故 / 被误解过（至少把不变量固化进去）；
3. 跨端 / 跨层多文件耦合（「改一个默认值要三处对齐」这类落点价值最高）；
4. 同一单元被第二个任务碰到（证明会反复来）。

| 段 | 必填 | 说明 |
|---|:----:|------|
| 行为契约 | 是 | 语义 / 输入输出 / schema，只写代码表达不了的 |
| 用户场景 | 是 | 谁在什么场景用、典型输入输出、验收口径、场景约束（场景约束即不变量）|
| 不变量 | 是 | 每条一句、尽量写成 audit 可核对的可判定陈述 |
| 落点与验证 | 是 | `- <repo路径>…` 源文件行（staleness.py 解析对象）+ 修改清单（跨文件对齐点）+ 验证方式 |

模板：[templates/spec.md](templates/spec.md)。代码事实一律反引号（check.py 锚点校验）。尾部留 `<!-- verified: <commit> -->`。

### 3.5 attention.md

**职责**：一行禁止句清单，服务快修任务的阅读经济学（读 10 行禁止句就够，不用吞 100 行 spec）。

**产生触发器**：红线**被踩过**（事故证明「读 spec 不变量」这条路径没拦住人），或 spec 长到快修任务读不起。**默认不建**——红线以不变量身份躺在 spec 里即可。**不预写。**

**准入**：只收「一行禁止句 + 指针」——`禁止 X，会炸 Y → 详见 spec#不变量 / adr-NNNN`。解释、完整契约、原理一律在 spec / adr，链过去。允许一句话的重复，不允许一段话的重复。

**归属**：红线住在**拥有它的单元**里。找不到归属单元的红线 = 缺一个 design 单元的信号，建那个机制单元，**不要造模块级的桶**。跨模块契约归拥有代码的模块的单元，本模块只在闭包里链过去、不复制。

模板：[templates/attention.md](templates/attention.md)。预算 ≤15 行。

### 3.6 adr/

**职责**：记录「为什么选 A 不选 B」，让后来者推翻现状前先付一次阅读成本，而不是重付一次学费。

**准入（三条 AND，都满足才写）**：
1. **难逆 / 高变更成本**：改回去要重构大量核心代码（底层数据库、核心通信协议、编排框架…）；
2. **缺上下文会让人意外**：未来的人看到会问「为什么不用更主流的 X」；
3. **存在真权衡**：不是对错题，而是为满足某指标（性能 / 隔离度 / 离线运行…）放弃了另一部分便利。

预期频率：**一个模块一年几条**。显然的 / 跟随惯例的决策不写。

**读取时机**：① 单元闭包「设计依据」点名；② **推翻现状前必查**该单元与模块 adr/。

**与规范层分工**：「以后都这么做」是规范 → 进 CLAUDE.md / conventions（agent 每次都读到）；「当时为什么这么定」才是 adr → 按需读。规范条目链回 adr 作出处。二者混写会让规范越写越长、adr 没人读。

| 文件 | 必填 | 说明 |
|------|:----:|------|
| `README.md` | 是 | 何时写 / 命名规则 / 当前 adr 列表 |
| `NNNN-短标题-kebab.md` | — | 单个 adr（编号四位单调递增，废弃用 `Status: Superseded by NNNN`）|

模板：[templates/adr.md](templates/adr.md)。

### 3.7 architecture.md / overview.md（按需）

- **architecture.md**：只装**跨 feature/design 的全局分层图 + 全局不变量**。能下放进某个 design 单元 spec 的细节必须下放。宁可少一层。
- **overview.md**：仅当模块 nav 清单超一屏才建（20-30 行摘要）；否则 nav 已覆盖其职责。

## 四、上下文完备性检验器（六件事）

评估单元文档是否完整、新文件类型提案是否冗余，用这张表。任何新文件类型提案先问「它提供六件中的哪一件」——答不上即冗余；某件在某单元无载体即缺失。

| # | 内容 | 回答的问题 | 载体 |
|---|---|---|---|
| 1 | 行为契约 | 改成什么样才算对 | spec 契约 + 场景 + 不变量 |
| 2 | 代码落点 | 动哪些文件、从哪进 | spec 落点段 |
| 3 | 依赖机制 | 我调用的下层契约是什么 | nav 闭包 → design/ |
| 4 | 约束红线 | 什么不能碰、动了炸什么 | spec 不变量 / attention |
| 5 | 决策背景 | 现状为什么长这样、别改回去 | adr |
| 6 | 验证方式 | 改完怎么证明没坏 | spec 验证段 |
| +7 | 影响面 | 谁依赖我（改契约 / 机制时）| `check.py --backlinks`（脚本反算，不人肉维护）|

## 五、回写规则（全部强制 / 立即 / 无需询问 user）

任何代码任务途中触发下列情形，**先回写、再继续手头任务**，禁止以「等任务做完再补」推迟。

| # | 触发情形 | 动作 | 写到哪 |
|---|---|---|---|
| R1 | index 粗筛 miss，靠横向比对 / grep 兜底定位成功 | 补关键词；模块缺行则 index 加行 + 建模块 nav | index / 模块 nav |
| R2 | 模块对但单元清单 miss | 建单元 nav 卡 + 清单表加行 | 单元 nav + 模块 nav |
| R3 | 靠语义联想 / 兜底才猜中的用户词 | 该词提升进 index 对应行或模块 nav 全集 | index / 模块 nav |
| R4 | 发现文档与代码不符 | **以代码为准**，就地修正后再继续任务 | 对应文件 |
| R5 | 走错门（进错单元才发现）| 补一条范围边界：误解 + 正确去向 | 进错的那个单元 nav |
| R6 | 改一处炸另一处（事故）| 肇事单元闭包补触发链接；被炸契约无载体则先建（spec 不变量或 attention）| 肇事单元 nav + 拥有单元 |
| R7 | 修完一个 bug | 排查经验一行（查什么日志 / 表 / 断点）| 该单元 nav 闭包或 attention |
| R8 | 一次性计划（plan）落地合入 | HEAD 事实并入 spec；取舍沉淀 adr；nav「设计依据」链 plan 存档；**plan 从此不作为 HEAD 被引用** | spec / adr / nav |
| R9 | audit / 演练发现 miss 或 stale | 同 R1–R4 | 对应层 |

**写作纪律**（与回写同级强制）：只写代码表达不了的事实；HEAD 原则；代码事实反引号；文件由内容压力产生（先塞 nav 卡再抽 spec）；短句列表不写段落。

## 六、成熟度与迁移

- **成熟度标记**：⏳ = 只有 nav 卡（闭包铺好，够导航）；✅ = nav + spec 齐全。`check.py` 校验：模块 nav 清单标 ✅ ⇔ 单元存在 spec.md。
- **on-touch 增量迁移**：任务碰到哪个模块，就把该模块升级到 v2 骨架；一次一个模块；**禁止为迁移而迁移的批量回填**。⏳ 单元同理，碰到才补 spec。空库从一个模块起步即可，不必先铺满。
- **plan 归宿**：一次性过程文档（需求 / 设计 plan）不进 codemap。落地后按 R8 处理：HEAD 事实进 spec、取舍进 adr、nav 链 plan 存档。plan 永不作为 HEAD 真相被引用。

## 七、通用写作原则

| 原则 | 说明 |
|------|------|
| 只写路由不写百科 | index / nav 不展开枚举值和 API 签名 |
| 百科归 spec | 完整细节放单元 spec |
| 短句优先 | 每字段短句列表，不写段落 |
| 可 grep | 关键词、类名、枚举值精确，方便后续 grep 验证 |
| 增量维护 | 新功能只需 nav 加一行 + 建单元目录 |
| 源文件可追溯 | spec 落点段标源文件路径，反引号包裹供锚点校验 |
| 各层各司其职 | index 管模块路由（极少变），模块 nav 管功能路由（随功能增减），单元 nav 管闭包，不越级塞低层细节 |

## 八、发现机制与维护

- **入口**：根 CLAUDE.md / AGENTS.md 里一段导航协议，要求任何代码任务的第一个工具调用读 `docs/codemap/index.md`（scaffold 时由 codemap-init 追加到项目根规则文件）。
- **收工必跑**：改完任何 codemap 文件，跑 `python3 docs/codemap/tools/check.py`——断链 / 孤儿 / 骨架 / 成熟度 / 锚点 / 行数预算干净再提交。
- **定期审计**：`staleness.py` 报「源码晚于文档核对时间」的单元；codemap-audit（低档模型 fan-out 逐单元对源码核实可判定陈述 → 高档模型按差异回写）保持同步。
- **路由质检**：`drills.md` 收真实 prompt + 期望命中单元；冷启动跑，**路由命中率是本系统唯一 KPI**，miss 按 R1–R3 回写。
